# The 32-bit renderer encodes in a 64-bit child process

The 32-bit renderer (`573Renderer32.exe`) hands every export frame to `573Encoder.exe`, a 64-bit process built from the same `MediaSink::Sink` code the 64-bit renderer runs in process. RTX 50 cards (Blackwell) and newer do not run 32-bit CUDA at all, and ffmpeg's NVENC encoders open their session through CUDA whenever they are given plain system-memory frames, which is how the renderer feeds them, so in a 32-bit process `h264_nvenc` and `av1_nvenc` fail to open on those cards while they work on an RTX 40. Rendering cannot move: the 32-bit game DLLs only load into a 32-bit process and the renderer's afp interaction is per-frame pointer work (docs/x86_build.md). Encoding can, because the sink's whole input is a BGRA buffer per frame.

Opening NVENC on a Direct3D 11 device inside the 32-bit process was rejected: nothing documents that 32-bit NVENC keeps working on Blackwell through Direct3D, and if it does today a later driver can take it away. Piping raw frames to a stock `ffmpeg.exe` was rejected because the renderer's own encoder settings (the per-format quality mapping, the HEVC alpha path, keyframe intervals) would have to be rebuilt as command lines. Frames travel through Boost.Interprocess `windows_shared_memory` rather than inline in the pipe messages, so a 4K frame costs one copy instead of a trip through the pipe's buffers; the control messages reuse the named pipe channel and FlatBuffers framing of ADR 0007.
